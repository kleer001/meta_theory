1 · Executive brief

Trace ROM Studio is an unusually well-built machine for the last two-thirds of a game's life and has almost nothing written down about the first third. It can take a game that already exists and ship it honestly — package it, gate it, market it without lying, and propagate the lesson to its siblings. It cannot tell you whether the game is any good, and it has never written down how anyone would know.

Altitude verdict: yes, the repo is operating above its foundation — and it is the textbook shape of it. The ladder from "can run a canvas" to "ships a game people play" has roughly six rungs. This repo has built rungs 4, 5 and 6 to a professional standard — a publishing runbook full of failure modes that report success, a release gate wired into CI so the marketing physically cannot precede the game, and a cross-repo convention-propagation system with a version pin, a directive format and a parser. Rung 2 — the craft of game design itself — is empty. There is no document in this repo that says what makes a core loop good, and four persona sheets that ask about it.

This is not a lapse of diligence. It is exactly the failure META_THEORY was written to name: every individual step was reasonable, the model answered each question at the altitude it was asked, and the accumulation is a studio that has a 215-line runbook on itch.io's form-validation behaviour and zero lines on difficulty curves.

The five things worth acting on, in order

  1. P1 — A CONTRACT-tier directive has already been silently destroyed. The ## [0.15.0] section of CHANGELOG.md was overwritten by the 0.16.0 bump. Its body survives, mis-filed under 0.16.0. This is the precise failure CONTRIBUTING.md warns about in writing, it happened in the studio's own repo, and nothing detected it — because the delivery mechanism has no test and CI does not run when it changes. Detail →
  2. P1 — Two shipped scripts cannot run from a fresh clone. capture.sh hard-depends on a file in a different, private GitHub repo at a hard-coded sibling path; post.sh requires a .ttf the template does not ship. Every daughter carries both. Detail →
  3. P1 — Write the missing rung. One page — call it DESIGN.md — that says what a good core loop is, so GAME-SHEET.md's questions have an answer key and the panel has a rubric instead of four temperaments. Detail →
  4. P2 — Beta is defined as "someone who isn't you plays it" and there is no playtest protocol. The single highest-value observation loop in game-making is one sentence long. Detail →
  5. P2 — Stop bumping. Twenty versions in thirty days, the last four all refining curator-outreach ranking for games that have not shipped. Adopt a rule that VERSION moves only when a game shipped or a daughter asked. Detail →

What this repo does not need: more process. It is already the most carefully-reasoned per-line body of studio prose I have read in a hobby repo, and that is also the diagnosis.

3 · The six lenses

3.1 · Cartographer — the ladder, and where this repo sits on it

The domain is solo browser-game production, concept to shipped itch.io release. The ladder a serious practitioner climbs, in learning order, with this repo's coverage marked:

RungWhat it isCoverageWhere it lives, or should
L0 · Arithmetic Git, JS, the canvas API, serving a page, a test runner. Complete template/, run.sh, package.json
L1 · Design foundation What a core loop is and what makes one hold. Uncertainty, feedback, mastery curve, game feel, the second-hour problem, when a toy is enough. ABSENT Nowhere. GAME-SHEET.md asks the questions; nothing answers them.
L2 · Production craft Prototyping, scoping to a vertical slice, playtest method, iterating on observation rather than opinion. Half Scope and slice are well handled in MAKING-A-GAME.md. Playtest method is one sentence: "someone who isn't you plays it."
L3 · Systems & tech Determinism, layered rendering, code/data separation, testable pure cores, boundary validation. Strong CLAUDE.md, compositor.js, rng.js, the test suite
L4 · Ship & publish Packaging, store-page mechanics, the platform's real failure modes, honest copy, launch beats. Expert publishing/ — and PUBLISHING-RUNBOOK.md is the best file in the repo
L5 · Studio meta Convention versioning across a family of repos; propagating a lesson learned in one game to the others. Novel VERSION + CHANGELOG.md + check_updates.py + the stamp

The verdict the Cartographer exists to produce: the goal ("raise game concepts into shipped games") lands at L4–L5. The rungs beneath it that are not established are L1 entirely and the observation half of L2. Are they safe to skip?

  • L1 is a load-bearing trap. Skipping it does not make games fail to ship — this studio will ship them. It makes them fail to be good, silently, with no diagnostic available, because the studio has no vocabulary in which "the loop is thin" is a checkable statement rather than a feeling. The panel is designed to catch exactly this and is given no criteria to catch it with: the Shipper asks "is there a core loop?", the Critic asks "does the mechanic say what the fiction says?", and nothing in the repo tells either of them what a good answer looks like. Four temperaments arguing without a rubric produce a mood, not a verdict.
  • The L2 gap is cheap to fix and expensive to leave. "Someone who isn't you plays it" is the right instinct pointed at the right moment, and it omits everything that makes a playtest worth running: don't explain the controls, watch the hands not the face, note the first hesitation, never defend the design in the room, write it down before discussing it. That is half a page. Without it, the beta label is a social event.

judgement The ladder above is a reconstruction; a different practitioner would split L3/L4 differently. The gap location is not sensitive to that — no plausible partition of this domain puts design craft anywhere but below publishing craft.

3.2 · Canon-finder — the foundation that was never written down

RESEARCH.md is emphatic: "Ground mechanics in precedent. Name the games, designers, and patterns an idea descends from… reach for the original (Rogue, 1980; not a 2024 listicle." The studio demands lineage of every game it raises and has recorded none of its own field's canon.

measured Every named external work in the entire repo, across all ~2,900 lines of prose: Rogue (1980), Ultima Underworld, System Shock, Dominion (2008), Slay the Spire (2017), and the Saul Bass AT&T globe (1983) in a code comment. All six sit inside persona character sheets or source comments, as illustrations of how a persona talks. Not one appears in a document a session would read to learn something.

The canon that is missing, ranked by how load-bearing it is for this studio specifically — a one-person, browser-game, short-session operation. Access status matters here per the canon-finder's own instruction: pin the gated ones now.

3.3 · Roots — four inventions with unnamed ancestors

The Roots lens asks what older disciplines a craft borrowed from, so its rules stop feeling arbitrary. Applied to this repo it produces something sharper than genealogy: four of the studio's five signature inventions have well-documented prior art the repo does not name. This matters not as an accusation of unoriginality — several of these are genuine improvements on their ancestors — but because RESEARCH.md makes lineage-tracing a house rule, and the house has not applied it to itself. Knowing the ancestor is also how you inherit its solved problems.

The inventionIts ancestorWhat the lineage would buy
The version stamp + directive + check_updates.py
A daughter records which template version it descends from; the template publishes changes; the daughter pulls them forward.		 Copier (and before it cookiecutter + cruft, Yeoman, Rails app templates). Copier writes _commit into .copier-answers.yml and copier update replays template changes onto the project. Copier solved this six ways and hit walls this repo will hit: what happens when the daughter edited the file the directive targets; how to record answers so an update is a three-way merge rather than a clobber; why never hand-edit the answers file is a hard rule. Trace ROM's version is deliberately different and better in one specific way — it delivers a proposal a reasoning agent interprets rather than a patch, which is the right call for prose conventions that no diff algorithm can merge. That is a real contribution and it deserves to be stated as such, against a named ancestor, instead of arriving unremarked.
The persona panel
Four standing lenses whose disagreement is the product.		 Schell's Book of Lenses (2008/2019) — the same move, at finer grain: 100+ named question-sets you aim at a design one at a time. Behind that, de Bono's Six Thinking Hats (1985) for the "one voice at a time, deliberately" mechanic, and red-teaming for adversarial review. Schell's lenses are criteria; this repo's panel is temperaments. That is precisely the L1 gap in miniature — the panel knows how four people would feel and not what any of them should measure. Mining Schell for the ten lenses that matter to a browser roguelike and stapling them to the persona sheets converts four moods into four checklists, at a cost of about a page.
The release gate — one hard stop, closed until it applies Aviation checklists via Gawande's Checklist Manifesto (2009), and specifically the DO-CONFIRM vs READ-DO distinction. The repo got this right by instinct and cannot currently defend it. RELEASE-CHECKLIST.md is a DO-CONFIRM list — you do the work, then confirm at a pause point — and the studio's insistence that it stay closed until beta, never be pre-ticked, and never be partially tracked is exactly the correct handling of that type. Naming the distinction turns three paragraphs of assertion into one sentence of citation, and tells a future session which other checklists in the repo are READ-DO (the publishing pre-publish checks) and therefore have opposite rules.
Budding — git subtree split then prune Named and handled correctly. BUDDING.md cites subtree split, filter-repo, bundle, fast-export, format-patch, and is honest that git rm prunes the tip and not the past. No gap. This is what the other three should look like.

The transplantable principle the Roots lens asks for: from the checklist lineage — a checklist is for the steps a competent person skips under load, not for the steps they do not know. The studio has applied this to shipping. It has not applied it to design, where the equivalent artifact would be a short list of the questions a designer reliably forgets to ask while excited about a mechanic. That is one plausible shape for the missing L1 document, and it is a shape this repo already knows how to build.

3.4 · First principles — the studio's own invariants, tested against itself

This repo is unusual in that it has largely derived its own first principles already; they are scattered through CLAUDE.md as terse, well-argued rules. Extracting them and testing each against the repo's own behaviour is the most productive thing this lens can do here.

The invariant, as the repo states itHeld?Evidence
One source of truth. "A sentence describing what the code does is a copy." Violated The house conventions — naming, boundary validation, test discipline, SOLID, commit format — are written out in full three times: CLAUDE.md § Code conventions, template/CLAUDE.md § Conventions + § Architecture, and template/README.md § Conventions. That is roughly 200 lines of near-duplicated prose, each copy free to drift, under a rule that forbids exactly this. The rule is applied ruthlessly to prose-about-code and not at all to prose-about-prose.
A rule nobody can check is a suggestion. (The repo never says this outright; it acts on it constantly — the PreToolUse hook, the CI grep, the Pages gate.) Held twice, broken once — at the worst spot The panel-name rule gets two enforcement mechanisms for a one-person studio. The CHANGELOG heading format — which CONTRIBUTING.md itself calls "machine-read — get it wrong and delivery breaks silently" — gets none, and broke silently. See W1.
A description nothing executes will rot. Applied asymmetrically Applied with real courage to SPEC-SHEET.md — deleting a design document once the code answers it is a genuinely unusual and correct call. Not applied to the ~2,900 lines of studio prose, which nothing executes either. The repo has one honest defence here (its reader is a future session, not the code) and it holds for PUBLISHING-RUNBOOK.md; it holds much less well for the third copy of the naming conventions.
Pay a gate's cost at the moment it is about. Held, and well The staging of publishing/ (opens when the slice plays), RELEASE-CHECKLIST.md (opens after beta), and the panel (convenes twice, on something playable) is the single best structural idea in the repo. It is why the apparatus is affordable at all.
Feedback from a shipped game is what improves a studio. (Never stated. Practised once.) Practised, undocumented, drying up Commit f817666: "harvest the dev-server, packaging and CI conventions from a daughter." That is the healthiest mechanism in the entire repo — a real lesson, learned in a real game, promoted to a convention. It has happened once in twenty versions. The other nineteen bumps were authored in the studio, about the studio. This invariant deserves to be written down and made the default justification for a bump.

3.5 · Altitude check — the present-tense verdict

"What would a master of this craft be surprised we don't have written down?" — cheapest fix first:

  1. What makes a core loop good (½ day). A working solo designer would be startled that a repo with four critique personas, a release gate and a marketing plan has no page answering the question all four personas are built to ask.
  2. How to run a playtest (1 hour). Beta is defined by an outsider playing it. Nothing says what to do while they do.
  3. Why this game uses a seeded PRNG (1 hour). The house rule "never Math.random()" is enforced culturally and by convention; the design reason randomness exists in a game — which uncertainty it is buying — is unwritten, so a game can be perfectly deterministic and perfectly arbitrary.
  4. The studio's own lineage (2 hours). Per §3.3. The repo demands this of every mechanic it raises.
  5. A design-canon index (2 hours). Per §3.2. Items 1–2 are free; pin the paywalled ones by title, author, edition and ISBN while the question is live.
  6. What a finished game taught the studio (ongoing). A short log of conventions harvested from daughters, so the bump ratio is visible and the healthy mechanism is the named one.

Note what is not on this list: nothing about publishing, packaging, CI, versioning, honesty policy, or code architecture. Those rungs are done. This is a narrow, cheap, one-week gap sitting underneath a month of excellent work.

3.6 · Pre-mortem — six months out

The story, told from February 2027:

Trace ROM Studio is at 0.41.0. The changelog is 1,900 lines. Three daughters are pinned at 0.13, 0.9 and 0.24, because adopting a directive costs a session and there are now thirty of them outstanding across the family — several superseded by later ones, with nothing in the format that says so. The last eleven bumps were about outreach copy, page metadata and the wording of the honesty guardrails. No game has shipped. The studio is in excellent health and produces documents about game-making.

The root cause is not laziness — it is that the repo has a feedback loop for process quality and none for game quality. Process improvements can be authored from inside the studio, in an afternoon, and they always feel productive. Game-design improvements require a game, a player, and an uncomfortable observation. When only one of those two loops is closed, the studio's effort flows into it by gravity, and every individual bump is defensible.

measured The trend is already visible: of the last ten version bumps, six concern publishing, marketing or process wording; one concerns game-facing platform behaviour (0.16.0, keyboard focus in the itch embed — and note that one came from a real platform failure, which is exactly the healthy kind); zero concern design craft. The three most recent bumps (0.17, 0.18, 0.19) are successive refinements of how to rank curators for outreach — a step no game in the family has yet performed.

The scaffolding that should exist now: the L1 document, so that "the loop is thin" becomes a sentence the studio can check rather than a feeling it can only have.

The single highest-leverage action before proceeding: a standing rule that VERSION does not move unless (a) a game shipped, (b) a daughter hit the problem in a real build, or (c) the change is to the design foundation. Commit f817666 is the model. Everything else waits in BREADCRUMB.md until a game asks for it. This costs nothing, requires no new document, and would have prevented three of the last four bumps.

4 · Main findings

4.1 · What is good

G1 · PUBLISHING-RUNBOOK.md is expert-tier and rare

215 lines of platform behaviour that is not discoverable from any dashboard, organised around a single correct principle stated in the second paragraph: "Every item is a failure mode that reports success." The itch.io form posting every field and silently reverting untouched ones; all-or-nothing validation where an over-length tagline discards edits to fields you did care about; the rich-text editor syncing into a hidden textarea; the "play in browser" flag clearing on every build replacement; screenshot deletion gated behind a confirm dialog that automation dismisses. This is the kind of knowledge that normally exists only as scar tissue in one person's head. Writing it down is the single most valuable thing in this repo.

G2 · The release gate is mechanical, not a promise

pages.yml greps RELEASE-CHECKLIST.md for the sign-off sentinel and physically deletes publishing/ from the Pages artifact until it is ticked. The marketing cannot precede the game it markets, and the enforcement is not a rule a session can forget. The workflow comment goes further and states the coupling as a hazard — "move the sentinel line and this step moves with it: a miss here withholds the page forever while the deploy still reports success" — which is the correct way to document a load-bearing string. Converting a policy into a mechanism is the repo's best habit.

G3 · "Never write a persona's words to a file" is a genuine insight

The reasoning is stated once and is right: "a constraint nobody can check the reason for is a constraint nobody can renegotiate." An invented character's opinion, written to disk, reads back next session as a specification — including to the assistant that invented it. Very few AI-assisted workflows have noticed this failure mode at all. judgement The enforcement is disproportionate (see F1), but the observation is a real contribution.

G4 · Proposal-not-patch is the right call for the update tie

check_updates.py prints directives and refuses to apply them; the pin only advances via an explicit --mark-read. For prose conventions — which no merge algorithm can reconcile — routing the update through a reasoning agent that reads the cited studio files and compares them to the game is strictly better than a diff. This is where the repo genuinely improves on its ancestor (§3.3), and the improvement is unclaimed.

G5 · The template code is small, pure and honestly tested

compositor.js is 65 lines and earns its abstraction: one contract ({ name, draw(ctx, frame) }), save()/restore() isolation between layers, and activeLayers() factored out as a pure function specifically so the ordering-and-visibility rule is testable without a canvas. The tests assert the contract — draw order, skip-when-disabled, save/restore nesting, boundary rejection — not the pixels, which is exactly the discipline CLAUDE.md demands ("a test asserts what the code implements; what merely follows from two rules meeting is an observation"). verified 15/15 pass.

G6 · Staged apparatus — each gate opens at the moment it is about

publishing/ closed until the slice plays; RELEASE-CHECKLIST.md closed until after beta, with explicit instructions not to pre-tick or track partial progress; the panel convening only on something playable; SPEC-SHEET.md deleted the moment code answers it. Each piece of apparatus is cheap precisely because it is worked once. This is what makes a process this heavy survivable at all, and it is the design decision most worth keeping.

G7 · BUDDING.md is honest about its own limits

Leads with the history-preserving path, marks the file-transfer variants as workarounds for a constraint rather than upgrades, gates the destructive prune behind a verification step, and closes by stating plainly that git rm prunes the tip and not the past — "don't claim the folder is 'gone from the repo' when its blobs are still in history." Correct, and correctly caveated.

G8 · Small earned lessons, kept

run.sh scans upward for a free port and says so when it moves, and sets no-cache headers because "a browser will serve stale JS on reload and you debug code that is not running." package.sh documents itch's three real constraints (index.html at the archive root, .zip only, <1000 files) and why zipping the project folder fails. test.yml installs only when a lockfile exists. Each is one comment long and each encodes an afternoon someone already lost.

4.2 · What is marginal

M1 · The conventions are written three times

Per §3.4: CLAUDE.md, template/CLAUDE.md and template/README.md each carry a full statement of naming, error handling, test discipline and commit format; the first two additionally duplicate the SOLID and code/data sections at length. There is a defensible reason for two of the three (the studio brief stays home; the game's brief travels after budding), and none for the third. Roughly 200 lines under a rule that forbids exactly this pattern.

M2 · The changelog only grows

664 lines and 19 releases in 30 days, with no supersession mechanism. Directives narrow and reverse each other in prose — 0.15.0's entry says of 0.12.0's, "this narrows the earlier sketchpad direction" — but a daughter pinned at 0.9.0 receives both and must reconstruct that relationship itself, from prose, one directive at a time. The entry format has Trigger, Read, Compare to, Action and Skip if, and no Supersedes.

M3 · The panel-name check is case-insensitive over ordinary English

The regex the (Shipper|Critic|Archivist|Superfan)'?s?\b runs with -i, so the sentence "the critic in me wants a second pass" fails CI in a daughter repo. More concretely, the hook and the CI check have different exemption lists: the hook exempts personas/, CLAUDE.md, CHANGELOG.md and .claude/hooks/; CI exempts only CLAUDE.md and test.yml. A daughter that writes a changelog entry explaining this very rule passes the hook and fails CI. verified — no current false positive exists in template/, so this is latent rather than live.

M4 · Vestigial and stale references

  • pages.yml still concatenates SPEC-SHEET.md when searching for the release sentinel — a legacy path from before 0.12.0 moved the checklist out, and before 0.15.0 established that the file is deleted entirely. Harmless, but it now documents a state that cannot exist.
  • .gitignore ignores trash_treasure/spike/artifact.html verified — a path belonging to a game that has budded (and under a name that does not match the surviving daughter, treasure_trash).

M5 · package.sh ships fonts the game does not use

RUNTIME=(index.html styles.css src fonts), under the comment "What a player needs at runtime." verified the template game does not use the VT323 face at all — styles.css sets font-family: monospace and index.html loads no font. The three .woff2 subsets exist for publishing/promo.html, which is not in the zip. Every itch upload carries dead weight, and the comment is false about its own array. Minor in bytes; it matters because it is one of the few places the repo's prose is wrong about its own code.

M6 · Shell strictness is inconsistent

run.sh, package.sh and capture.sh use set -euo pipefail; post.sh uses set -uo pipefail, dropping -e. Plausibly deliberate — a batch encoder should not abort the whole run because one take is missing — but it is undocumented in a repo that documents everything, and "one path, fail loudly" is a house rule.

M7 · Semver where the tier already carries severity

Every change is a minor bump, including four CONTRACT-tier breaking changes marked ! in their commit subjects. Defensible under 0.x, and the CONTRACT/TIGHTEN/CLARIFY tier is doing the real work of communicating severity — which means the semver component is a monotonic counter wearing a version number's clothes. Not wrong; just be aware the number carries no information a daughter can act on.

4.3 · What is wrong

W1 · A CONTRACT directive was silently destroyed by the next bump verified

The 0.16.0 bump commit 7fce55a did not insert a new release section above 0.15.0 — it overwrote the 0.15.0 heading line:

$ git log --oneline -S'## [0.15.0]' -- CHANGELOG.md
7fce55a feat(publishing): the embedded game reclaims its own keyboard focus   # removed it
b8a2f4e feat(template)!: the spec sheet is pre-code scaffolding...            # added it

$ git log -S'## [0.15.0]' -p -- CHANGELOG.md | grep -E '^[-+]## \['
-## [0.15.0] — 2026-08-05
+## [0.16.0] — 2026-08-10

The 0.15.0 body — a CONTRACT-tier directive, "the spec sheet is pre-code scaffolding, and it comes down" — survives, now sitting as the second entry under ## [0.16.0]. Consequences, in order of severity:

  1. Version 0.15.0 is unreachable. entries_between() selects sections by heading; no 0.15.0 heading exists, so no daughter can ever be told what 0.15.0 was.
  2. A daughter stamped exactly 0.15.0 — the stamp any game copied from the template between 2026-08-05 and 2026-08-10 carries — is re-served a directive it has already acted on, mislabelled as a later version's.
  3. This is the exact failure CONTRIBUTING.md warns about in writing: "a release heading typed at the wrong level is skipped entirely, folding its directive into the section above and delivering it under someone else's version." The document that predicts the failure did not prevent it, because prediction is not a check.
  4. Nothing detected it, and nothing could have. check_updates.py validates that a bracketed heading parses as semver; it does not validate that versions are contiguous, monotonic, or that VERSION has a matching section. And CI never ran: the only workflow in the mother repo is template-tests.yml, filtered to paths: ['template/**']. A commit touching CHANGELOG.md, VERSION and scripts/ triggers no CI at all. verified

This is the most important finding in the report, and not because a spec-sheet directive went missing. It is because the studio's single delivery-critical machine-read format — the thing the entire mother/daughter architecture rests on — is the one artifact in the repo with no test, no CI, and no validator, in a repo that hooks the Write tool to enforce a naming convention.

W2 · capture.sh depends on a different, private repo at a hard-coded sibling path verified

HERE="$(cd "$(dirname "$0")/.." && pwd)"
RECORDER="$HERE/../utilities/window_recorder.sh"
[ -x "$RECORDER" ] || { echo "recorder not found: $RECORDER" >&2; exit 1; }

For a budded daughter at ~/code/my-game/, that resolves to ~/code/utilities/window_recorder.sh, which lives in github.com/kleer001/utilities — a separate repository. The dependency is undeclared in publishing/, in video_shot_list.md, in PUBLISHING-RUNBOOK.md, in RELEASE-CHECKLIST.md and in template/README.md, all of which describe capture.sh as a thing you run. It works on exactly one machine, by accident of directory layout, and fails on every fresh clone of every daughter — including a clone made by the author on another machine. The script also assumes xdotool and a live X11 session with no stated prerequisite.

W4 · The template ships no LICENSE verified

template/package.json declares "license": "MIT". CLAUDE.md lists MIT as a house platform default. RELEASE-CHECKLIST.md has [ ] LICENSE present as a gate item. ITCH-PAGE.md tells the player "Source is open (MIT)." The mother repo has a LICENSE file. template/ does not, so every budded daughter starts life unlicensed, asserting MIT in three places, until someone notices at the release gate — which is the last possible moment and after the code has been public for the whole of alpha. package.sh also omits any licence file from the itch zip while shipping the VT323 subsets, whose OFL terms require the notice to travel with the font.

W5 · The delivery mechanism has no test, in a studio that requires tests for new behaviour

CLAUDE.md: "new behavior gets a test that fails before the change and passes after." check_updates.py is 171 lines of parsing, version comparison, section extraction and stamp mutation, and has zero tests. The test suite covers mulberry32 (17 lines, trivially correct), the logo's scanline geometry (123 lines, cosmetic) and the compositor (65 lines, well covered). The studio tested the three things that were easy to test and left the one whose failure would be invisible — and it then failed invisibly, per W1. judgement This is the cleanest illustration in the repo of the general pattern: effort flows to the loop that closes.

4.4 · What went too far

F1 · Two enforcement mechanisms for the panel-name rule, in a one-person studio

A PreToolUse hook on Write|Edit that blocks the tool call, and a CI step that fails the build, and a paragraph in CLAUDE.md, and a paragraph in template/CLAUDE.md, and a paragraph in personas/README.md, and a note in MAKING-A-GAME.md — for a rule whose only possible violator is the person who wrote it. The underlying insight is excellent (G3). The response is the "make it impossible" reflex applied to a problem that "notice and delete it" already solves, and it now costs a regex over common English nouns in every daughter's CI (M3) forever. judgement Keep the hook, which is instant and free and catches the real case mid-session. Drop the CI step, which runs on every push of every daughter to catch a write the hook already blocked.

F2 · Optimising a step nobody has performed

Versions 0.17.0, 0.18.0 and 0.19.0 are three successive refinements of how to vet a curator before pitching them — is the outlet still publishing (pull the feed, read the newest pubDate, drop anything quiet three months); is it actually read (median engagement across the last ten posts, not follower count); is it a format match (read the last twenty titles, ask what shape they share). The reasoning is genuinely good and the Bluesky/YouTube/WordPress measurement recipes are practical. It is also roughly 40 lines of increasingly refined instruction for a task that no game in this family has reached, and it now sits in the delivery queue of three daughters, at least one of which is a prototype. This is what the pre-mortem is pointing at, in its purest form.

F3 · A document whose principal content is its own disclaimer

template/SPEC-SHEET.md is 39 lines. Roughly 22 of them explain that the file has no authority, is not a promise or a contract, will be deleted when the slice plays, and that git history keeps it. Roughly 12 are the actual prompts. The decision is right and unusually clear-headed. The implementation is a page that spends most of itself arguing against its own existence — which suggests the honest form is four bullet points at the top of GAME-SHEET.md under a heading like "scratch, delete when it plays," and no file at all. The strongest evidence for this reading is that the studio has now spent three separate CONTRACT-tier directives (0.12.0, 0.15.0, and the 0.16.0 re-file) adjusting what this file is allowed to be.

F4 · The prose-to-code ratio

measured ≈2,900 lines of prose to 288 lines of game source. Some of that prose is load-bearing and excellent (G1). But a studio brief that a session must hold in context before writing a line of game code is itself a scoping decision, and this one now costs more to read than the thing it describes costs to write. judgement The three-way convention duplication (M1) is where to cut first, because it is the part no argument defends.

4.5 · What didn't go far enough

S1 · No design foundation at all

The headline gap. See §3.1 and A1. The repo has a research-honesty gate, a code-architecture standard, a publishing runbook, a release gate and a convention versioning system, and no answer to "is the game good."

S2 · No playtest protocol behind the beta definition

See A2. The one loop that produces information the studio cannot generate by reasoning is the one loop with no procedure.

S3 · The runbook's claims are unsourced and undated — under the repo's own strictest rule

RESEARCH.md: "Claims about the real world… are held to primary evidence… Cite when it matters." PUBLISHING-RUNBOOK.md is the most claim-dense file in the repo — every paragraph asserts a specific behaviour of itch.io or YouTube, down to a verbatim error string (short_text: expected text between 1 and 120 characters, or empty) — and carries no source or date on any of it. Direct experience is primary evidence and is almost certainly where this came from; the problem is that nothing records that, so in twelve months no reader can distinguish "I hit this on 2026-07-31" from "I believe this," and platform behaviour is exactly the class of fact that expires. A one-line Observed: 2026-07-31, itch.io dashboard under each section costs nothing and is what the studio demands of every game it raises.

S4 · Budding is verified once, by hand, and never again

BUDDING.md step 3 correctly gates the destructive prune on "the new repo clones fresh and runs in isolation." That check happens once, manually, at bud time. Three daughters are now loose with no mechanism that would notice if one stopped passing its own tests, lost its Pages deploy, or drifted off the platform. The mother has a check_updates.py that pushes conventions out and nothing that reads anything back. judgement A twenty-line script that walks a roster of daughter paths and reports pin, test status and last commit would close this, and is a smaller investment than any of the last four directives.

S5 · The one healthy feedback mechanism is undocumented

Commit f817666 — harvesting conventions from a daughter — is the correct direction of information flow and has happened once. It is not named in CONTRIBUTING.md, which describes only how to author a convention in the studio and push it down. Making harvest the documented default path for a bump, and studio-authored directives the exception requiring justification, would restructure the repo's incentives at a cost of one paragraph.

5 · Advice — the mother repo

Ordered by leverage. Everything in tier A is a day or less; nothing here requires restructuring.

Tier A — do these first

A1 · Write the missing rung: a design foundation P1

  • Where: DESIGN.md at the studio root, pointed at from CLAUDE.md with the same "read when…" framing the other pointers use — read when you are shaping the pitch and again when the slice first plays.
  • Length: one page. This document earns its place by the standard the repo already sets for prose (its reader is a future session, and nothing in the code can state it), and it fails that standard the moment it grows into a textbook.
  • Content — five questions with actual criteria, not four temperaments:
    1. What is the loop, in one sentence, and what does the player learn by repeating it? (Koster: fun is a pattern being learned; when there is nothing left to learn, it is boredom regardless of production values. This is the operational form of the Critic's "second hour.")
    2. Which uncertainty is this game selling? (Costikyan's taxonomy — performative, solver's, randomness, hidden information, narrative anticipation. The studio mandates a seeded PRNG in every game and has never said what the randomness is for; a game can be perfectly deterministic and perfectly arbitrary.)
    3. Split the pitch M / D / A. (Hunicke et al. — mechanics are what you build, aesthetics are what the player feels, dynamics are what happens in between, and a pitch that names an aesthetic with no mechanic that produces it is the "CRT filter over a game about nothing" failure the Critic persona already describes without a name for it.)
    4. Where is the input latency, and what does the action feel like? (Swink. On a hand-rolled canvas loop, every frame of lag is the studio's own doing and nothing else in the repo mentions it.)
    5. What is the failure state, and does losing teach anything?
  • Then wire it to the panel: give each persona sheet a line pointing at the question it owns. The Shipper owns 1 and 5, the Critic owns 3, the Superfan owns 1's long tail, the Archivist owns the lineage question already in RESEARCH.md. This converts four moods into four checklists at a cost of four lines, and is the single change that would most improve the panel's output.
  • Cost: half a day, of which most is reading the two free sources (R1, R2).

A2 · Write the playtest protocol P1

  • Where: a section in MAKING-A-GAME.md under the beta label, where the definition already lives.
  • Content: the canonical shape, from Fullerton (R4) — recruit someone who has not seen it; explain nothing beyond "here it is"; watch the hands and the first three hesitations, not the face; never defend the design in the room; write your notes before you discuss it; and the one rule that does most of the work — what a tester says is data about what they felt, not instructions about what to build.
  • Why it is P1: this is the only information channel in the studio that cannot be simulated by reasoning harder, and it is currently one sentence.
  • Cost: one hour.

A3 · Put a check on the delivery mechanism P1

  • Add scripts/test_check_updates.py — or a --validate mode on the existing script — asserting: every ## [X.Y.Z] parses; versions are strictly descending down the file; no version is skipped; the newest heading equals VERSION; template/.trace_rom_studio_version equals VERSION; every Read: path exists on disk. Each of those five would have caught a real failure — W1 trips the third and fourth.
  • Widen the CI path filter. template-tests.yml is scoped to paths: ['template/**'], so the changelog, VERSION and scripts/ are outside CI entirely. Add a second job, unfiltered, that runs the validator.
  • Then repair W1: restore a ## [0.15.0] heading above its own directive body, leaving 0.16.0 with only the keyboard-focus entry that belongs to it. The fix is one line; the value is that the version becomes reachable again and the family's history stops lying.
  • Cost: two hours including the tests.

A4 · Fix the four shipped defects P1

  • W2 — capture.sh: either vendor window_recorder.sh into publishing/ (it is ~3 KB and MIT-compatible if you own it), or state the dependency at the top of the script and in template/README.md and fail with an actionable message naming the repo to clone. Vendoring is the right call — a launch tool that only runs on one machine is not a tool the template can honestly ship.
  • W3 — post.sh: ship VT323-Regular.ttf alongside the subsets (the OFL permits redistribution with the notice, which fonts/ already carries), or default FONT to a system face and document the substitution.
  • W4 — template/LICENSE: add it. Add it to package.sh's RUNTIME array too, alongside fonts/VT323-OFL.txt if fonts stay in the zip.
  • M5 — package.sh: drop fonts from RUNTIME until a game actually uses the face, and make the comment true.
  • Cost: an hour, all four.

Tier B — structural, worth a weekend

B1 · A bump needs a reason from outside the studio P2

Add to CONTRIBUTING.md: VERSION moves only when (a) a game shipped and taught something, (b) a daughter hit the problem in a real build, or (c) the change is to the design foundation. Commit f817666 is the model and should be cited as such. Everything else waits in BREADCRUMB.md — which already exists, already says "work the studio owes itself," and is currently empty. This is the single highest-leverage line in this report against the pre-mortem failure, it costs one paragraph, and it would have deferred three of the last four bumps.

B2 · Give directives a Supersedes: field P2

Per M2. One new field in the entry format, and one rule in check_updates.py: when printing a range, mark any directive superseded by a later one in the same range as context, already narrowed by. A daughter at 0.9.0 currently receives 0.12.0's "the spec sheet is a sketchpad," then the 0.15.0 body's "…and it comes down," and must work out from prose that the second replaces the first. Making that machine-visible is what stops directive debt compounding.

B3 · Collapse the three-way convention duplication P2

Per M1. Keep two copies with a stated reason: the studio brief (CLAUDE.md) and the travelling brief (template/CLAUDE.md), which must stand alone after budding. Cut the third — template/README.md § Conventions — to a pointer at ./CLAUDE.md. The README's job is what this is and how to run it, which it does well in its Layout and Run sections. This is the repo's own DRY rule, applied to the repo.

B4 · Date and source the runbook P2

Per S3. One Observed: YYYY-MM-DD line per section, and where a behaviour came from documentation rather than experience, the link. Platform behaviour expires; a runbook whose claims have no date cannot be audited, and this studio audits everything else.

Tier C — worth doing, no urgency

  • C1 · Name the lineage. A short § Prior art in CONTRIBUTING.md (Copier / cookiecutter for the update tie) and in personas/README.md (Schell's lenses, Six Thinking Hats). Per §3.3 — the repo requires this of every mechanic it raises, and it makes the genuine improvements legible as improvements.
  • C2 · Retire the CI half of the panel-name check and keep the hook. Per F1. If it stays, at minimum drop the -i flag and align its exemption list with the hook's.
  • C3 · Add a daughter roster and a read-back script. Per S4. ~20 lines: walk a list of paths, print pin vs VERSION, test status, last commit date. This is also the smallest useful version of the maestro.md idea, aimed at one family.
  • C4 · Clean the vestigial references. The SPEC-SHEET.md leg of the pages.yml grep; the trash_treasure/ line in .gitignore. Per M4.
  • C5 · Reconsider SPEC-SHEET.md as a file. Per F3. Three CONTRACT directives have now been spent on what this file is allowed to be; a "Scratch — delete when it plays" section at the bottom of GAME-SHEET.md would end the argument permanently.
  • C6 · Document post.sh's missing -e or add it. Per M6.

6.1 · Should the daughters be audited separately?

Two of the three: no. One: yes, and for a reason that has nothing to do with drift.

The convention drift will titrate down fine. That was the right instinct. The update tie exists, it works — verified check_updates.py runs clean against the template — and the outstanding directives are mostly process wording that a daughter's own session can adopt in one pass. Running a full META_THEORY audit on treasure_trash or coincidence-engine would rediscover the mother's L1 gap three more times, because a daughter cannot have a foundation the mother never wrote. Fix the mother, then let the pipe carry it.

The exception is the two shipped defects (W2, W3) and the missing LICENSE (W4). Those are not conventions — they are broken files and a legal omission that every daughter is already carrying. They need a directive, not an audit.

The one worth a look is coincidence-engine, and not for its pin. Its last commit is "chore: rebuild the publishing copy" — a game working on its launch surfaces while pinned nine releases back, which means it is at the publishing stage under 0.9.0-era rules and has never received the 0.11.0 CONTRACT directive that wires the Pages deploy to the release gate. That specific combination — publishing activity on a stale pin — is the one state where drift is not cosmetic, because it is the state where a placeholder landing page can go public. Ten minutes with check_updates.py, not an audit.

6.2 · What to send down the pipe, and in what order

The correct delivery vehicle is the mechanism the studio already built. Three bumps, in this order — and note that this ordering is itself an application of B1: each is a real defect a daughter is carrying, not a studio-authored preference.

  1. A CONTRACT directive for the broken launch scripts and the licence. Covers W2, W3, W4 in one entry: Trigger — the game has publishing/ or intends to release; Compare to — does publishing/capture.sh resolve its recorder, does fonts/VT323-Regular.ttf exist, is there a LICENSE; Action — adopt the vendored recorder, take the TTF, add the licence file. This is the one with real consequences, so it goes first.
  2. A CLARIFY directive re-pointing at the repaired changelog. Once W1 is fixed, a daughter that has already read the mis-filed 0.16.0 section should know 0.15.0 is not new work. Small, but it keeps the family's history honest — and the studio's own CONTRIBUTING.md rule about renumbering already establishes the etiquette for this.
  3. A TIGHTEN directive for the design foundation, once A1 exists. Trigger — the game has a playable slice; Read — DESIGN.md; Compare to — the game's GAME-SHEET.md; Action — answer the five questions against the running game and propose changes where an answer is missing or thin. This is the directive that actually improves the games, and it is the one that cannot be written until the mother has the document.

6.3 · Standing advice for every daughter

  • Run check_updates.py at each stage transition — not on a calendar. The natural moments are: the slice first plays, content-complete, and the release gate. This matches the studio's own "pay the cost at the moment it is about" principle and keeps directive debt from being a background anxiety.
  • Adopt the pin discipline the studio states but does not enforce: --mark-read only after the directives are actually resolved, never to clear the queue. An advanced pin with unadopted directives is worse than a stale one, because it is a lie the tooling now believes.
  • A daughter is allowed to refuse a directive — every entry has a Skip if for exactly this — but the refusal should land in a commit message. Otherwise the next session re-litigates it, which is the same failure the studio's own "say who decided" rule is guarding against.
  • Harvest upward. If a daughter solves something the template got wrong — as one already did for the dev server, packaging and CI — that is the highest-value bump the studio can receive. Per S5, make this the expected direction rather than the exception.

7 · Conclusions

1. The repo is very good at what it is good at, and the gap is narrow, specific, and cheap. This is not a report about a project in trouble. Rungs L3, L4 and L5 are built to a standard most one-person studios never reach, and PUBLISHING-RUNBOOK.md alone justifies the repo's existence. The prescription is roughly one week: one page on design, half a page on playtesting, a validator, and four small fixes.

2. The failure is structural, not personal, and it is the exact one META_THEORY predicts. Every bump was reasonable in isolation. The model answered each question at the altitude it was asked, and no question was ever asked at L1 — so the studio accumulated a month of excellent work on top of a rung that was never built. That is why the altitude check is designed to be recurring: the drift is invisible from inside the work, and it feels like productivity the entire time.

3. The deepest pattern: effort flows to whichever loop closes. Process improvements close in an afternoon, alone, and always feel productive. Design improvements need a game, a player, and an uncomfortable observation. This repo tested the three easy things and left the delivery mechanism untested, wrote 215 lines on itch.io's form validation and none on difficulty, and enforced the persona rule twice while the changelog format — which it correctly identified in writing as silently breakable — broke silently. Every one of those is the same choice, made honestly, several times. B1 is the counterweight: make a bump require a reason from outside the studio, and the gravity reverses.

4. The mother/daughter architecture is a real contribution and is currently unclaimed. Proposal-not-patch — routing a template update through a reasoning agent that reads the cited files and argues with the user, rather than through a merge algorithm — is a genuine advance over the Copier lineage for the specific case of prose conventions, which no diff can merge. It deserves to be stated against its named ancestor. The same repo that requires every mechanic to name its lineage has not named its own.

5. On the daughters: fix the mother and let the pipe carry it — with the three exceptions in §6, which are broken files rather than conventions and need a directive now.

6. Re-run the altitude check when DESIGN.md exists and a game has shipped, not on a calendar. Those are the two events that will change the answer. Everything else is noise on a one-person studio.
